Dependencies and compatibility ​

This page covers how a mod names other mods it needs, orders itself after them or refuses to run with them.

Dependency entries ​

dependencies in mod.json holds at most 32 entries. Each entry is { "id", "range", "kind" }.

  • id is the other mod's id.
  • range is a version range: *, 1.2.3, ^1.2.0, ~1.2.0 or >=1.0.0 <2.0.0. It defaults to *.
  • kind is required, optional or incompatible.

required ​

The mod cannot run without the other one.

json
{ "id": "carina-team.prism-optics", "range": "^1.0.0", "kind": "required" }
  • If the other mod is not switched on in the same game, the game reports missing-dependency.
  • If it is switched on but out of range, the game reports dependency-version.
  • Switching the mod on in RULES switches its installed required mods on, and theirs in turn.
  • In ONLINE CATALOG, INSTALL installs the missing required mods from the catalog with the mod. The detail pane lists them under Also installs: <mods>.

optional ​

The mod works with or without the other one.

json
{ "id": "acme.extra", "kind": "optional" }
  • If the other mod is absent, nothing happens.
  • If it is switched on, it must be in range (dependency-version otherwise), and it loads first.

incompatible ​

The mod cannot share a game with the other one.

json
{ "id": "acme.other-mod", "range": "^1.0.0", "kind": "incompatible" }

If the other mod is switched on and in range, the game reports the error incompatible.

loadAfter ​

loadAfter is a list of mod ids in mod.json. It orders two mods that are both on and adds no requirement.

json
{ "loadAfter": ["carina-team.prism-optics"] }

Load order ​

The phase orders the load: the game's rules, then the profile, then content, patch and final mods. Within a phase, mods load in dependency and loadAfter order, then by id. The RULES picker shows the order.

A patch mod therefore sees every record of every content mod. That is what a compatibility add-on needs.

Conflicts ​

Two mods conflict when nothing orders them (no dependency, no loadAfter, the same phase) and both set the same path. They also conflict when one removes a record the other changes. The RULES picker asks the player to pick a winner. List operations from several mods combine.

Declare a dependency or loadAfter when your mod builds on another, and the conflict does not arise.

Example ​

Choir Prisms is a compatibility add-on. It has no records, pictures or text, only patch rows. It requires Prism Optics and Hollow Choir and loads after both. It gives empires that have the Resonance pick Refractive Optics at the Average start. Prism Optics gives that field to everyone at Advanced and keeps it out of Post-Warp, so the example has no Post-Warp row:

json
{
  "op": "append",
  "catalog": "start-state",
  "key": "classic",
  "path": "levels.average.alsoKnown",
  "value": {
    "field": "carina_team.prism_optics.refractive_optics",
    "when": { "picks": ["carina_team.hollow_choir.resonance"] }
  }
}

A game with all four mods composes in the order carina.base, carina.profile.standard, carina-team.hollow-choir, carina-team.prism-optics (unrelated, so by id) and carina-team.choir-prisms.

Finding dependencies when testing ​

check, run and pack look for the mods a folder requires in the other folders of mods/. To name a folder elsewhere, add --with <folder>:

sh
npx carina-modkit check mods/choir-prisms
npx carina-modkit check ../elsewhere/my-add-on --with mods/prism-optics --with mods/hollow-choir

The Check my mod page checks one mod at a time, so it reports a required mod as missing.
